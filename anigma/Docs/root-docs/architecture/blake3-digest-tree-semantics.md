# BLAKE3 Digest Tree Semantics Roadmap

## Status: Planned

TD source of truth: `td-062215` ("BLAKE3 digest tree semantics and evidence integration").

## Why This Exists

SaturationKit currently has a verified BLAKE3 compression-block primitive and a Metal one-block parity test. That is not the same as a full BLAKE3 digest. Full BLAKE3 semantics require a hasher state machine around the compression function: chunking, chaining values, parent-node reduction, keyed modes, derive-key modes, and root output.

Until this roadmap is complete, production code must not treat the current `AnigmaPrimitives.BLAKE3Digest` compatibility shim as real BLAKE3. TD notes identify that shim as SHA-256-backed API compatibility.

Implementation priority: build a full CPU BLAKE3 digest/tree implementation first. That CPU implementation is the correctness foundation, official-vector target, and golden oracle for hardware acceleration. Once it is solid enough to retire or rename the SHA-256 shim, move as much of the digest/evidence pipeline as practical into Metal, and later ANE-aware scheduling where it fits.

## Required Semantics

### 1. CPU Digest And Tree Hasher

Implement the official BLAKE3 state machine in SaturationKit:

- 1024-byte chunks.
- 64-byte blocks.
- chunk counters.
- partial final block handling.
- `CHUNK_START`, `CHUNK_END`, `PARENT`, and `ROOT` flag handling.
- chaining-value stack for tree reduction.
- root output node generation.
- XOF-ready output block generation.

Caller-facing APIs should expose digest semantics, not raw compression:

```swift
Blake3Digest.hash(_ data: Data) -> Blake3Digest
Blake3Digest.keyedHash(_ data: Data, key: Blake3Key) -> Blake3Digest
Blake3Digest.deriveKey(context: String, material: Data) -> Blake3Key
```

The compression primitive remains useful for tests and Metal kernels, but it should not be the normal receipt/evidence API.

### 2. Official Reference Vectors

Tests must use official BLAKE3 reference vectors rather than values generated by Anigma's own implementation.

Coverage must include:

- empty input.
- 1, 63, 64, and 65 bytes.
- 1023, 1024, and 1025 bytes.
- multi-chunk inputs.
- keyed hash mode.
- derive-key context and material modes.
- first 32, 64, and 128 bytes of XOF output if XOF is implemented.

### 3. Metal Chunk Chaining-Value Kernel

After the CPU implementation passes official vectors and the SHA-256 compatibility shim is retired or renamed, the first GPU stage should produce chunk chaining values from many independent 1024-byte chunks. This gives a correctness-first hardware path without forcing the full tree into one kernel.

Required proof:

- Metal chunk CV output matches CPU chunk CV output.
- tests skip cleanly when no Metal device exists.
- Metal validation passes when a device exists.

### 4. Metal Parent Reduction And Root Finalization

The second GPU stage reduces chunk chaining values pairwise using parent-node compression. The CPU implementation remains the oracle for every Metal stage. Root finalization can be staged:

1. CPU full digest/tree hasher proves semantics against official vectors.
2. SHA-256 compatibility shim is retired or renamed.
3. GPU chunk CV generation.
4. GPU pairwise parent reduction.
5. CPU fallback for the final small tail if necessary.
6. Later fusion only after correctness is stable.

Required proof:

- Metal digest equals CPU digest across chunk-boundary and multi-chunk inputs.
- command buffer and resource usage pass `MTL_DEBUG_LAYER=1`.

### 5. Replace The SHA-256 Compatibility Shim

`AnigmaPrimitives.BLAKE3Digest` must stop returning SHA-256 under a BLAKE3 name, or callers must migrate to explicitly named compatibility APIs.

Migration rules:

- BLAKE3-named APIs return real BLAKE3 only.
- SHA-256 fallback APIs are named as SHA-256 or compatibility paths.
- receipt/evidence code cannot silently accept SHA-256 where BLAKE3 is declared.
- tests fail if a BLAKE3-named API returns the SHA-256 digest for a known input.

### 6. Evidence Receipt Wiring

Saturated evidence receipts and heartbeat payload hashes must use the real BLAKE3 digest API.

Evidence records should distinguish execution substrate:

- CPU BLAKE3 fallback.
- Metal chunk/tree BLAKE3.
- future in-kernel rolling heartbeat BLAKE3.

All three must share the same digest semantics.

### 7. Mission Descriptor Hash Policy

Decision for `td-b8344d`:

- Keep SHA-256 for Tier-1 mission descriptor signatures for descriptor `version = 1`.
- Name this policy explicitly as `sha256Tier1V1`; descriptor versions without an explicit mapping are rejected.
- Bind signatures to the explicit descriptor-hash policy and reject mismatches during verification.
- Keep descriptor-signing hash computation CPU-only for deterministic cross-device parity (no Metal/ANE acceleration for this path).
- Continue using real BLAKE3 for evidence/receipt and hardware-accelerated digest workloads.

This preserves Ed25519 interoperability and signature stability while avoiding algorithm ambiguity in descriptor validation.

### 8. Integration And Regression Tests

Final integration must prove:

- CPU digest matches official vectors.
- Metal digest matches CPU digest.
- receipt IDs use real BLAKE3 where the contract says `BLAKE3(JCS(payload))`.
- heartbeat payload hashes use real BLAKE3.
- migrated callers no longer route through the SHA-256 compatibility shim.

## Execution Order

1. Implement full CPU BLAKE3 digest/tree semantics.
2. Validate against official BLAKE3 vectors.
3. Retire or rename the SHA-256 compatibility shim.
4. Migrate production BLAKE3-named callers to the real digest API.
5. Add Metal chunk-CV acceleration.
6. Add Metal parent reduction/root finalization where it wins.
7. Evaluate ANE-aware scheduling after GPU and CPU semantics are stable.
8. Wire hardware-accelerated BLAKE3 into saturated evidence receipts.

## Exit Criteria

This epic is complete when:

- BLAKE3 digest/tree semantics match official vectors.
- Metal BLAKE3 digest output matches CPU output for representative inputs.
- no BLAKE3-named production API returns SHA-256.
- saturated evidence receipts and heartbeat payload hashes use real BLAKE3.
- mission descriptor hash policy is documented, versioned, and tested.
