Anigma Accessibility Atlas

A guide to the Anigma ecosystem and its accessibility-first architecture.

The Foundational Framework

Anigma is the shared foundation for a new generation of intelligent, accessible applications. It provides a clean, robust, and reusable core based on an **Entity-Component-System (ECS)** architecture. This design promotes a clear separation of data (Components), logic (Systems), and identity (Entities), which is essential for building complex, maintainable software.

Core Concepts

  • Entity: A unique identifier, representing an object like a document, a user, or a request.
  • Component: Pure data attached to an entity, such as a name, a file path, or a status.
  • System: Stateless logic that operates on entities with specific components, like a system that processes all documents needing OCR.
  • World: The container that manages all entities, components, and systems, ensuring data integrity and thread safety.

This modular architecture allows different applications, like `Harmonia` (the AI brain) and `Apertum Accessum` (the student-facing client), to share the same underlying structure while implementing their own unique features.

The Four Pillars of Accessibility

Our commitment to accessibility is codified by targeting **WCAG 2.2 Level AAA**, the highest global standard. This framework is organized around four core principles, known as **POUR**.

1. Perceivable

Users must be able to perceive the information being presented; it can't be invisible to all of their senses.

  • Providing text alternatives for non-text content (like images).
  • Ensuring high contrast between text and background.
  • Allowing users to resize text up to 300% without breaking the layout.
  • Not relying on color alone to convey information.

2. Operable

Users must be able to operate the interface; the interface cannot require interaction that a user cannot perform.

  • Making all functionality available from a keyboard.
  • Giving users enough time to read and use content.
  • Not designing content in a way that is known to cause seizures.
  • Providing clear focus indicators for all interactive elements.

3. Understandable

Users must be able to understand the information as well as the operation of the user interface.

  • Making text readable and understandable.
  • Making web pages appear and operate in predictable ways.
  • Helping users avoid and correct mistakes with clear error messages and confirmation dialogues.

4. Robust

Users must be able to access the content as technologies advance. Content must be robust enough that it can be interpreted reliably by a wide variety of user agents, including assistive technologies like screen readers.

  • Maximizing compatibility with current and future user agents, including assistive technologies.
  • Using semantic HTML and native UI components correctly.

From Principle to Practice with Apple's HIG

WCAG principles provide the "what," and Apple's Human Interface Guidelines (HIG) provide the "how." Here is how we translate WCAG AAA goals into practical implementation on macOS and iOS.

WCAG AAA Goal Apple HIG Implementation
High Contrast (Perceivable)
Ensure a minimum 7:1 contrast ratio for text.		 We strictly adhere to Apple's color system, support Light/Dark Modes, and provide a dedicated High-Contrast theme. We use tools to verify our color palettes meet this ratio.
Text Resizing (Perceivable)
Allow text to be resized up to 300% without loss of content or functionality.		 Our apps fully support Dynamic Type. All layouts are built to reflow gracefully when the user adjusts their system-wide text size, ensuring no content is clipped or obscured.
Keyboard Accessible (Operable)
All functionality must be available via keyboard.		 We implement full keyboard navigation, ensuring every interactive element is reachable via the `Tab` key. We design visible Focus Rings so users always know where they are.
Text Alternatives (Perceivable)
Provide labels and descriptions for non-text content.		 We use SwiftUI's Accessibility API extensively. All icons and images have descriptive .accessibilityLabel() for VoiceOver, and decorative elements are hidden with .accessibilityHidden(true).
Feedback & Error Handling (Understandable)
Provide clear feedback and help users correct mistakes.		 We use native alerts and confirmation dialogues to prevent data loss. Error messages are clear, human-readable, and suggest a path to recovery, following HIG patterns for system feedback.
Reduce Motion (Operable)
Respect user preference for reduced motion to avoid vestibular triggers.		 Our application queries the system's "Reduce Motion" setting. When enabled, all non-essential animations are disabled or replaced with simple cross-fade transitions.
Robustness with Assistive Tech
Ensure compatibility with screen readers and other tools.		 By using native SwiftUI components and correctly applying accessibility traits (e.g., .isButton, .isHeader), we ensure that VoiceOver and other assistive technologies can interpret and present our UI reliably.
