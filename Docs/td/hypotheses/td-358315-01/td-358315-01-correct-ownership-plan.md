## Correction: Ownership, Not Visibility Inflation

**Original error:** Proposed making LayoutEngineCapsuleWrapper internal types `public` to satisfy AnigmaPipeline cross-module access.

**Why this is wrong:**
- Internal declarations are visible only inside their defining module (Swift access control)
- Public declarations are visible from importing modules
- Making implementation types public to satisfy a compiler error **expands API surface** and risks turning implementation details into contracts
- The correct fix is **correct target ownership**, not visibility inflation

## Correct Ownership Decision

### Why PDFLayoutExtractContract Belongs in PDF-Specific Target

1. **Not in generic registry:** NOT registered in `PipelineContractRegistry`
2. **PDF-specific implementation:** Calls `PDFLayoutExtractWrapper.analyzePDF` which calls `LayoutEngineCapsuleWrapper` (PDF layout engine)
3. **PDF-specific types:** Uses internal LayoutEngineCapsule types that are inaccessible from AnigmaPipeline
4. **Module boundary violation:** AnigmaPipeline (generic) is reaching into LayoutEngineCapsule implementation details

### Split Decision

**PDFLayoutExtractContract has TWO concerns:**

| Concern | Location | Ownership | Fix |
|---------|----------|-----------|-----|
| Contract interface (id, schemas, validate) | PDFLayoutExtractContract | Could be portable | Keep in PDF-specific target |
| Implementation (execute using LayoutEngineCapsule) | PDFLayoutExtractContract.execute | PDF-specific | Move to PDF-specific target |

**But:** The contract's validate and execute both use PDF-specific types (PDFPageLayout, PDFLayoutSegment, etc.) that are defined in terms of LayoutEngineCapsule internal types via `internal init(from: PageLayout)` etc.

**Conclusion:** The **entire** PDFLayoutExtractContract + PDFLayoutExtractWrapper should be in a **PDF-specific target**, not in generic AnigmaPipeline.
